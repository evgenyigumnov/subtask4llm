# План: поддержка Pi coding agent отдельным скиллом

## Цель

Добавить устанавливаемый отдельно скилл `subtask4llm-pi` для Pi coding agent. Он должен выполнять многошаговый план через последовательные одноразовые процессы `pi`, передавая результат завершённых шагов только их зависимым шагам. Существующий `subtask4llm-codex` и его поведение остаются независимыми.

## Что уже есть в репозитории

- Скиллы лежат в `skills/<skill-name>/`; README описывает независимую установку каждого.
- `skills/subtask4llm-codex/` содержит инструкции, Python-runner, формат JSON-плана версии 1, тесты и метаданные для Codex.
- Текущий runner обеспечивает последовательный запуск, ограниченные повторы, проверку результата, dry-run и защиту от рекурсивного запуска.
- Pi поддерживает Agent Skills со стандартным `SKILL.md`; каталог `.agents/skills/` распознаётся Pi. У Pi CLI есть одноразовый `--print` и флаг `--no-session`. В отличие от Codex CLI, `--print` возвращает финальный текст агента, поэтому Pi-runner должен сам потребовать JSON и проверить его после запуска.

## Предлагаемая структура

```text
skills/
└── subtask4llm-pi/
    ├── SKILL.md
    ├── scripts/
    │   └── run_workflow.py
    ├── references/
    │   └── plan-format.md
    └── tests/
        └── test_run_workflow.py
```

Скилл должен быть самодостаточным: установка одного `subtask4llm-pi` не должна зависеть от файлов внутри `subtask4llm-codex`. Формат JSON-плана версии 1 и контракт результата шага следует сохранить совместимыми с Codex-версией.

## Этапы реализации

### 1. Создать описание Pi-скилла

Добавить `skills/subtask4llm-pi/SKILL.md` со стандартным frontmatter (`name: subtask4llm-pi`, содержательное `description`) и инструкциями для Pi в роли планировщика и ревьюера. Описать критерии выбора workflow, подготовку плана, обязательную передачу контекста изолированным исполнителям, показ пользователю порядка шагов перед запуском и проверку итогового отчёта.

Инструкции должны объяснить установку Pi и наличие настроенного провайдера как предварительные требования, но не предлагать устанавливать Pi автоматически. Pi-worker запускается из скрипта с `--no-session` и `--no-skills`, чтобы не сохранять рабочие сессии и не вызывать этот же скилл рекурсивно. Контекст репозитория, включая `AGENTS.md`, должен оставаться доступным. Указать, что процессы Pi выполняют команды и редактируют файлы с правами текущего пользователя; сам CLI не является песочницей.

**Готово, когда:** Pi видит корректное описание скилла, может выбрать его по задаче и получить из него точную команду запуска runner.

**Статус: выполнено.** Добавлен самостоятельный `skills/subtask4llm-pi/SKILL.md` с выбором workflow, планированием, командами запуска для macOS/Linux и Windows, требованиями к Pi/provider и описанием разрешений.

### 2. Реализовать самостоятельный Pi-runner

Создать `skills/subtask4llm-pi/scripts/run_workflow.py`. Взять за контракт текущий JSON-план версии 1 и формат результата шага из Codex-скилла, но не импортировать его код и не вызывать `codex`.

Runner должен:

- проверять план, уникальность шагов, ссылки только на предыдущие зависимости и непустые критерии приёмки;
- запускать не более 10 шагов строго последовательно в одном workspace и завершаться при первом неуспешном шаге;
- формировать worker prompt из общего контекста, карты всего плана, деталей текущего шага и результатов только объявленных зависимостей;
- вызывать Pi без shell через `pi --print --no-session --no-skills`, передавать prompt через stdin и использовать `--model`, если он задан;
- проверять JSON-ответ worker по той же схеме результата, которую использует Codex-runner; неуспешный exit code, некорректный JSON или неверная схема считаются неуспехом шага;
- поддерживать `--workspace`, `--dry-run`, `--timeout-seconds`, `--retries` (0 или 1), `--max-summary-chars`, `--artifacts-dir`, `--pi-bin` и необязательный выбор модели через `--model`/`PI_WORKFLOW_MODEL`;
- блокировать вложенный workflow с отдельными переменными окружения, не изменяя существующие `CODEX_WORKFLOW_*`;
- не сохранять сессии Pi; артефакты сохранять только по явному запросу и не перезаписывать существующий каталог.

Не включать `--mode json` только ради структурированного результата: JSON mode выдаёт поток событий, а не гарантированный JSON-объект ответа. Использовать финальный текст `--print`, требовать от worker сырой JSON без Markdown-ограждения и строго валидировать его.

**Готово, когда:** корректный dry-run показывает порядок шагов и итоговые параметры запуска без вызова Pi; рабочий запуск корректно принимает только валидный результат и останавливает workflow по ошибке после настроенного повтора.

**Статус: выполнено.** Самостоятельный runner добавлен; его dry-run, выполнение с fake Pi, проверки результата, повторы, timeout, recursion guard и артефакты проверены.

### 3. Добавить формат плана и инструкции для запуска

Создать `skills/subtask4llm-pi/references/plan-format.md`, перенеся описание JSON-плана версии 1 и добавив Pi-команду запуска и dry-run. Команды должны использовать `python3` на macOS/Linux и `py -3` на Windows, как в текущей документации.

Обновить корневой `README.md`: добавить установку `subtask4llm-pi` через Skills CLI с `--agent pi`, не меняя существующую Codex-команду. Сверить перед реализацией, что текущая версия Skills CLI по-прежнему поддерживает цель `pi` и Pi обнаруживает проектный `.agents/skills/`.

**Готово, когда:** обе команды установки, Codex и Pi, представлены в README, а отдельный формат-план объясняет использование и ограничения Pi-runner.

**Статус: выполнено.** Добавлен формат плана Pi и команда независимой установки в README; существующая команда Codex сохранена.

### 4. Покрыть поведение Pi-runner и проверить независимость скиллов

Добавить изолированные тесты с поддельным `pi` executable. Проверить валидацию планов, CLI-аргументы и окружение, порядок шагов и передачу зависимостей, dry-run без реального запуска, отсутствие сессий/скиллов, обработку таймаута, повтор, остановку после повторной ошибки, а также отклонение отсутствующего, некорректного и несоответствующего схеме результата.

Проверить оба скилла: тесты нового runner проходят, тесты существующего Codex-runner не требуют изменения поведения; каталоги каждого скилла можно установить независимо. При наличии установленного Pi выполнить ручную проверку обнаружения скилла и `/skill:subtask4llm-pi`; вызов модели не должен быть обязательной частью автоматических тестов.

**Готово, когда:** тесты используют только mock Pi, Codex-скилл остаётся без регрессий, а Pi-команда установки указывает на правильный скилл.

**Статус: выполнено.** Все 15 тестов Pi-runner прошли. Один из 13 тестов Codex завершается с ошибкой, которая также воспроизводится на чистом `HEAD`; Codex-файлы в этой работе не менялись.
